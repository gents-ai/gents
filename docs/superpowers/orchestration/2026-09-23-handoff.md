## 6. Self-improving loops: where GEPA fits

Everything built so far is the **acceptance side**: contract, runner, first definition, calibration,
policy, guarded promotion. A wrong acceptance makes the system quietly worse; a weak proposer only
makes it slow. That is why every candidate-generation technique comes after M6, and why none of
them touches the statistics or the promotion guard. They all plug in ahead of the gate.

The loop as it exists on the stack (optimization spec sections 3 to 7): freeze a baseline, run the
train split, ask the `Proposer` for a new target text, build the patch deterministically in
`target.rs`, run train then validation on the candidate, judge with `PolicyV2` (permutation test
on paired per-case scores, non-regression, cost), append the decision to the `OptimizationJob`
journal, repeat; a final held-out confirmation in `Confirm` mode; an operator promotes through
`with_expected`. Role separation is by construction: the proposer holds no `ConfigAccess`,
solvers run inside trial homes, verdicts carry per-check `feedback` on the train split only.

| Piece | What it is | When | What already exists |
|---|---|---|---|
| **M7, GEPA 1: reflective proposer** | An LLM reads the train-split verdict feedback and the rejection history and writes the next candidate text | First thing after M6; the umbrella names it "the LLM proposer and its evidence projection" | The `Proposer` trait and `ProposalInput` (current text, train verdicts with feedback, rejection history); rejection memory is the journal. Spec 2 of the optimization design fixes the shape: an ordinary `AgentRequest` on a dedicated behavior with no write grants, `RenderedRequest` excluded from its evidence. M7 is a second trait implementation plus the sanitized evidence projection; no new machinery |
| **M8, GEPA 2: Pareto archive, multi-candidate rounds, merge** | Keep a frontier of candidates each best on some case; sample parents from it | After M7, needs a brainstorm and spec; listed as a v1 non-goal in the optimization spec | Per-case scores (`case_means_bp`, case as clustering unit) are already the unit, so a frontier derives from existing verdicts with no schema change |
| **M9, SIFT: judge pre-filter with Bradley-Terry ranking** | Cheaply rank many candidates with an LLM judge, send only the top few to the full paired eval | After M8; only pays off once a round has several candidates | `llm_judge` is a development-tier check by design, so a judge can never count toward acceptance; the permutation gate stays the only thing that accepts |

Research ranking (`20-ranking.md`): shared substrate P0 (now on the stack), GEPA reflective
evolution 6, decision gates 6 (the A/A measurement, M5), SoL-Pi recall tool and ObservationPack 5,
SIFT build 3. Procedural Graphs contributes loop discipline (gated commits, rejection memory), which
the driver already follows. The binding constraint the research named was eval signal, not
optimizer sophistication: with 6 to 8 validation cases a Pareto frontier has little to be Pareto
over, so M8 and M9 become worth building once M3's case count grows.

Path: M3 calibration → M5 → M6 live job → M7 spec (brainstorm) → M7 → M8 → M9. The user wants

# Conformance pipeline audit — defra-agent runtime

Date: 2026-05-14

Scope: every emitted Lean vector family in `Proofs/Conformance/Contracts/Json.lean`, the Rust deserialization layer in `crates/defra-agent/src/lean_vocab_test.rs`, the consumer registry in `crates/defra-agent/tests/support/conformance_consumers.rs`, the coverage ledger in `crates/defra-agent/proofs/Proofs/Conformance/CoverageLedger.lean`, and the runtime consumer tests (primarily in `tests/state_machine_conformance.rs`, plus `tests/apply_conformance.rs`, `tests/live_overlay_conformance.rs`, `tests/identity_conformance.rs`, and the per-module `*::tests` blocks the ledger points at). This audit is the input for the parallel Rust catch-up wave after the #183-tracker Lean burst.

Bottom line: the pipeline is mostly wired — 26 of 28 substantive vector families round-trip from Lean JSON into Rust and most of those are consumed by tests that actually drive the runtime against the Lean witness. **Three drift bugs need attention before any catch-up PR ships.** First, PRs #199 and #202 added ledger entries for `streaming_response_cases` and `compaction_reducer_cases` without adding Lean JSON emitters, Rust deserializers, Rust tests, or even adding the new categories to the ledger drift-test's `valid_categories` list — which means the drift test (`state_machine_conformance::lean_contract_coverage_ledger_accounts_for_every_emitted_domain`) currently fails closed any time it actually runs. Second, identity vectors (PR #196) emit + deserialize + are consumed by `tests/identity_conformance.rs`, but the consumers are *not* in the registry and the ledger has no entries for them, so the same drift test silently ignores both halves of the bridge. Third, four "shape-pinning" consumer tests — `generated_transcript_cases_pin_agent_message_ordering_contract`, `event_delivery_transition_cases_match_contract`, `event_delivery_source_instances_match_runtime`, `event_delivery_convergence_traces_match_runtime_or_deviation` — assert what the Lean cases look like but do not drive the corresponding Rust runtime (hook persistence, Watcher, EventSource, SubagentSource) and compare. They are registered as `consumerCoverage` though they are operationally equivalent to `consumerWithFollowUpCoverage`.

## Per-family verdict

### ✓ Wired (24 substantive families + vocabularies/state_machines/boundaries/deviations/follow_up_hooks)

Each of these emits a Lean witness, has a 1:1 deserializer in `lean_vocab_test.rs`, has a ledger entry that names a registered consumer, and that consumer actually drives the Rust runtime against the witness:

- **Vocabularies (15 domains).** 13 have Rust round-trip tests under `lifecycle::tests`, `runtime_status::tests`, `admission::tests`, `mcp_pool::tests`, and `tool_call_lifecycle::tests`. Three (`AwaitMode`, `CancelPolicy`, `ChildTerminal`) are explicit `followUpCoverage` pending the subagent R4 consumer (`CoverageLedger.lean:115-126`); they have no Rust round-trip yet by design. Two (`PersistenceState`, `PersistenceFailurePolicy`, `StorageObservation`) are `boundaryCoverage` because the runtime persists state behind a hook policy and the vocabulary is checked at the storage boundary instead of the in-memory enum.
- **State machines (11 domains).** 7 have direct Rust contract tests; 4 are boundary entries (Persistence × {failOpen,failClosed}, StorageObservation × {failOpen,failClosed}) that are checked operationally by `state_machine_conformance::lean_executable_contracts_cover_initial_domains`. 3 (`AwaitMode`/`CancelPolicy`/`ChildTerminal`) are `followUpCoverage` pending subagent R4. PairingReconcile rides on the same executable-contracts test, which is the lightest check on the list — the state machine is large enough that this is worth a follow-up.
- **`request_transition_cases` / `process_transition_cases`.** Deep conformance — every legal case is driven through the live transition and the classification + writer action are compared; every illegal/productUnreachable case is asserted to have no writer path.
- **`trigger_dispatch_cases`.** The Rust trigger engine's `dispatch` function is driven by every Lean case (35+ cases at last count).
- **`apply_reconcile_cases`.** Drives the production `diff()` function and asserts buckets, step ordering, prefix safety, manifest reference closure, and re-apply convergence. Closest thing in the pipeline to a property-based test.
- **`session_recovery_cases`.** Tokio + embedded node — actually inserts rows, runs reissue, asserts deadlines and lineage post-state. Heaviest test on the list.
- **`inference_slot_accounting_cases` / `fleet_slot_accounting_cases`.** Drive `slot_contribution()` / `reconstructed_running_slot_count()` per case and assert the slot capacity invariants.
- **`backend_health_admission_cases`.** Drives the `backend_registry` admission decision per case.
- **`native_filesystem_boundary_cases`.** Drives `toolset` boundary contract per case.
- **`tool_preflight_cases` / `tool_retry_cases`.** Drive the preflight + retry disposition tables.
- **`command_policy_cases` / `command_sandbox_cases` / `command_env_cases`.** Drive the policy/sandbox/env decision tables — these are the most thoroughly cased table in the entire pipeline.
- **`live_overlay_cases`.** Drives `should_show_overlay()` per case.
- **`mcp_health_cases`.** Drives a Rust-simulated K=1 health tick per case and asserts `HealthStatus` matches the Lean projection. PR #198 added this with full round-trip wiring in one shot — the model for how an emitter-side PR should land.
- **`runtime_reconcile_cases`.** Drives `runtime_status_generation_updates_match_lean_runtime_reconcile_cases` per case.
- **`frontend_client_shell_cases` / `desktop_client_shell_cases`.** Driven by TypeScript and Rust tests respectively; the only family with a two-implementation consumer split.
- **`boundaries` / `deviations`.** Metadata is exercised by the two `lean_*_metadata_*` tests, which assert every boundary id used elsewhere is declared here and every deviation is classified.

### ⚠️ Partial (4 families — shape-pinning but no runtime drive)

These have a ledger entry, a deserializer, and a test that *does* fail if the Lean case shape drifts — but the test does not exercise the corresponding Rust runtime. They are operationally indistinguishable from `consumerWithFollowUpCoverage`, but only `queue_deadline` and `recovery_sweep` declare that intent in the ledger.

- **`transcript_conformance_cases`.** `state_machine_conformance::generated_transcript_cases_pin_agent_message_ordering_contract` (`tests/state_machine_conformance.rs:789-868`) asserts the six named cases exist and that their `pre/post_message_count`, `pre/post_tool_call_count`, `expected_ordered`, `expected_pair_closed`, and `expected_strong_drain` fields match expectations. It does not feed any case into `crates/defra-agent/src/hook/persistence.rs` or `hook.rs` to verify that the actual AgentMessage append + dedupe + drain code respects the contract. The ledger marks this `consumerCoverage`, which overstates the coverage. Gap: the formal-coverage audit (`2026-05-13`) called out "AgentMessage persistence + ordering" as the highest-leverage gap in the entire runtime, and even now the Rust runtime is not driven against the model.
- **`event_delivery_transition_cases`.** `event_delivery_transition_cases_match_contract` (`tests/state_machine_conformance.rs:4772-4811`) walks the Lean cases and verifies their `pre`/`post` worlds are internally consistent with the action (Persist/Handle/RescanTick). It does not step the Rust `Watcher`, `EventSource`, or `SubagentSource` through the same actions.
- **`event_delivery_source_instances`.** `event_delivery_source_instances_match_runtime` (`tests/state_machine_conformance.rs:4813-4860`) pins three named source instances (Watcher / EventSource / SubagentSource) plus their `dedupe_policy`, `rescan_bounded_by`, and `deviation` fields. The pinned values match what the Lean model says about those sources — they do *not* match any introspection from the Rust source impls. The test name "match_runtime" promises more than it delivers.
- **`event_delivery_convergence_traces`.** `event_delivery_convergence_traces_match_runtime_or_deviation` (`tests/state_machine_conformance.rs:4862-4933`) verifies that every Lean trace tagged `substantive` actually converges and every trace tagged `deviation` actually fails to converge under the Lean transition rules. Again, no Rust source is stepped through the trace. Same name issue.

### ❌ Follow-up (2 families — intentional, well-documented)

- **`queue_deadline_conformance_cases`.** Ledger explicitly marks this `consumerWithFollowUpCoverage` (`CoverageLedger.lean:277-281`) with reason "Runtime-backed queue/deadline consumers land in R4a Task 5 and Task 7 after the Rust claim and scheduler implementations exist." The current test (`generated_queue_deadline_cases_pin_r4a_contract_rows`) pins per-case metadata so the contract is fenced against drift, and the runtime drive lands when the R4a Rust pieces exist. Operational risk: low — the missing pieces are tracked work, not silent gaps.

## Drift findings

### §1. Ledger drift-test would panic when run

`state_machine_conformance::lean_contract_coverage_ledger_accounts_for_every_emitted_domain` (`tests/state_machine_conformance.rs:359-650`) is the runtime cross-check that the ledger matches the snapshot, every consumer resolves, and every snapshot domain is fenced. Today it would panic for three independent reasons:

1. **`compaction_reducer_cases` and `streaming_response_cases` categories are not in `valid_categories`.** The assertion at `tests/state_machine_conformance.rs:581-585` (`valid_categories.contains(&entry.category.as_str())`) would fire on the very first of these two ledger entries because the category list at `:549-575` was last updated in PR #198 (mcp_health) and has not been extended for PRs #199 / #202. The diff is one line per category.
2. **Those same ledger entries name consumers that aren't registered.** The assertion at `:614-620` (`registered_consumers.contains(entry.consumer.as_str())`) would fire on `state_machine_conformance::generated_compaction_reducer_cases_pin_contract` and `state_machine_conformance::generated_streaming_response_cases_pin_lifecycle_contract` because `tests/support/conformance_consumers.rs:64-345` has no entries for them.
3. **`identity_structural_cases` and `identity_contracts` snapshot fields are not enumerated in the `emitted` set.** The `for vocabulary in ...` / `for machine in ...` / `if !snapshot.*.is_empty()` block at `:369-547` never inserts the two identity categories into `emitted`, so the `missing = emitted - ledger` / `extra = ledger - emitted` symmetric-difference assertion at `:631-640` is consistent only by accident.

If the test is currently passing in CI, it is because the consumer-side panics in (1) and (2) fire *before* the symmetric-difference comparison in (3) is reached — i.e., the test is monotonically broken in two places at once. The user-visible symptom is "every PR after #198 that touches the ledger fails the conformance test, but the panic message points at the new entries, not the missing infrastructure."

Why this matters: this test is the *only* automatic enforcement that the ledger and the snapshot agree. While it is broken, ad-hoc ledger entries can land without their JSON emitter or Rust consumer — which is exactly what happened with #199 and #202.

### §2. Identity vectors (PR #196) round-trip without a ledger entry

PR #196 (`Add Lean model for AgentPrincipal / AgentBehavior / AgentDeployment split`) added two vector families to `snapshotJson` (`Json.lean:506-509`), the corresponding `LeanIdentityStructuralCase` / `LeanIdentityContract` deserializers (`lean_vocab_test.rs:599`, `:608`), and a real consumer file at `tests/identity_conformance.rs` with three tests:

- `identity_structural_cases_match_lean_verdicts` — for every case, computes the Rust `rust_well_formed(case)` predicate and asserts it matches `case.well_formed`. This is a deep conformance test.
- `identity_structural_cases_cover_named_scenarios` — asserts six named scenarios exist (e.g., `amy_general_and_amy_code_share_principal`).
- `identity_respects_principal_contract_is_declared` — asserts the `identity.respects_principal_boundary` contract is `enforced=false` and `tracked_by="#193"`.

The Rust side is solid — `rust_well_formed` is an explicit mirror of `Identity.World.WellFormed` from `Proofs/Identity/State.lean`, and the test references "the future runtime permission engine (#193)" to keep the deferred-enforcement boundary discoverable.

The gap is that nothing connects this to the rest of the pipeline:

- `CoverageLedger.lean` has no entry for `identity_structural_cases` or `identity_contracts`.
- `conformance_consumers.rs` has no `RustTest` entries for the three `identity_conformance::*` tests.
- The ledger drift test's `emitted` set never includes the two identity categories (`tests/state_machine_conformance.rs:369-547`).
- The category list `valid_categories` (`:549-575`) has no identity rows.

Net effect: identity is wired end-to-end inside its own file but is invisible to the cross-cutting drift checks. Any future identity vector that lands without its consumer would be caught only by the standalone `identity_conformance.rs` test file failing — not by the ledger drift test.

### §3. `compaction_reducer_cases` and `streaming_response_cases` are dangling ledger entries

PRs #199 (streaming response, commit `e43b612`) and #202 (compaction, commit `3386fc9`) each added five lines to `CoverageLedger.lean` referencing `consumerWithFollowUpCoverage` for new vector families, plus the Lean module that defines the cases. Neither PR touched `Proofs/Conformance/Contracts/Json.lean`, `lean_vocab_test.rs`, `conformance_consumers.rs`, or `state_machine_conformance.rs`. The result:

- `Proofs/Compaction/Executable.lean:32-58` defines `compactionReducerCases` (10 entries). `Json.lean` does not import `Proofs.Compaction.Executable` and does not emit a `compaction_reducer_cases` JSON field. The `LeanContractSnapshot` struct (`lean_vocab_test.rs:27-72`) has no `compaction_reducer_cases: Vec<...>` field. There is no `LeanCompactionReducerCase` struct, no `lean_compaction_reducer_cases()` accessor. The ledger names `state_machine_conformance::generated_compaction_reducer_cases_pin_contract` as the consumer — that function does not exist anywhere in the repo. The consumer is not in `conformance_consumers.rs`. The category `compaction_reducer_cases` is not in `valid_categories`.
- `Proofs/StreamingResponse/Executable.lean:31-258` defines `responseTransitionCases` (12 entries, named `beginEmitsStreamingEmpty`, `writeTokensAdvancesProgress`, … through `bridgeCompletedPairsRequestCommitted`). Same story: no Json emitter, no struct, no field, no accessor, no consumer test, no registry entry, no category.

Both PRs claim "vectors are stable and ready" in the follow-up reason text. The vectors are stable in Lean — but they don't reach Rust. A reader of the ledger today would see two `consumerWithFollowUpCoverage` rows and conclude "the Lean is leading; the Rust catch-up is pending." The truth is that not even the bridge exists; the Rust catch-up is more than a test — it's a deserializer, a snapshot field, and a Json.lean import.

Difference from §1: the ledger drift test catches this *if* it runs (and the categories are added). Until then, this is silent.

### §4. `lean_executable_contracts_cover_initial_domains` is a weak consumer for PairingReconcile

`CoverageLedger.lean:162-165` registers `state_machine_conformance::lean_executable_contracts_cover_initial_domains` as the consumer for the `PairingReconcile` state machine. That same test is also named as the consumer for four boundary state machines (`Persistence.failClosed`, `Persistence.failOpen`, `StorageObservation.failClosed`, `StorageObservation.failOpen`). The function lives at `tests/state_machine_conformance.rs:47-222`. Walking it: it asserts that the named state machines have non-empty state lists, non-empty terminal-state lists, internal consistency of transitions, and (importantly) it does *not* compare PairingReconcile transitions to the Rust pairing-reconcile module. PairingReconcile has a real Rust implementation (`crates/defra-agent/src/agent/reconcile/slot.rs`, `crates/defra-agent/src/agent/reconcile/diff.rs`) that warrants a dedicated executable-contract consumer test in the shape of `request_state_machine_contract_is_complete`. Not strictly drift, but the ledger entry is misleading — it implies a level of fence the consumer test does not deliver.

### §5. Subagent vocabulary/state-machine follow-up entries (3 + 3) are correctly pending

`AwaitMode`, `CancelPolicy`, `ChildTerminal` appear as `followUpCoverage` entries in both `vocabularyCoverage` and `stateMachineCoverage` (`CoverageLedger.lean:115-127`, `:178-189`). These are explicitly waiting on subagent R4 wiring; the absence of a Rust consumer is expected and properly classified. Not drift; called out here for completeness because the seed list mentioned them.

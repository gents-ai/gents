Design notes

Tauri command surface

Snapshot of currently-backgrounded tool calls is consumed from desktop_operations_snapshot(request) as defined in spec §"Panel 5" / Panel 1 data-source sections. There is no separate list_backgrounded_tools() command — that name appeared in the PROMPT.md draft and was dropped to match the spec.

Snapshot fields consumed

  • liveness.active_tool_calls[] — supplies tool_name, request_id, tool_call_id, started_at, deadline_at, await_mode, running_age_ms, deadline_expired.
  • liveness.active_native_executors[] (when active_native_executors_available) — supplies id, pid, argv0, tool_name, started_at, age_ms. Correlated to a tool call by (tool_name, started_at) inside a ±1s window. The bridge never claims a PID it did not see in the live liveness payload, so the Process column is best-effort.
  • AgentToolCall projection — supplies lifecycle_state, cancel_policy, child_request_id, cancel_cascade_intent_at, cancel_pending_remote_ack, stuck_since. Primary rows are await_mode = "background" with non-terminal lifecycle_state.
  • AgentRequest projection — supplies session_id, subagent_depth, caused_by_parent_request_id, caused_by_parent_tool_call_id for lineage.

Stuck-tool visual treatment

A row is rendered as stuck (amber inset border, amber Status pill) when either:

  • AgentToolCall.stuck_since is set and the dwell since that timestamp exceeds 5 seconds (the spec's 5s rule, not PROMPT.md's draft 60s figure), or
  • AgentToolCall.cancel_pending_remote_ack is set.

Banner-level surfacing follows the spec auto-clear rule: the banner appears when expired_processing_count > 0 or any row meets the stuck criteria, and clears only after a clean snapshot is continuously observed for 5 seconds. A flaky bridge does not flap the banner because dwell is wall-clock-based, not snapshot-count-based.

Per-row actions

  • Open lineage selects the Lineage tab in OperationsRail and calls desktop_list_subagent_tree with the parent request id. No mutation.
  • Interrupt parent opens the cascade preview for the row's parent request via desktop_preview_interrupt_cascade; confirmation calls desktop_interrupt_request. This is the only cancel-style entry point; per-tool cancel is intentionally absent (see Divergences).

Accessibility

  • Column headers are sortable and reachable via Tab; Enter or Space toggles sort.
  • Arrow Up / Arrow Down on a focused row moves selection; Enter focuses footer actions.
  • The Age column ticks every second; updates are announced via a polite ARIA live region in batches (no per-second flood for screen readers).
  • Status pills carry a text label, not just colour — colour-blind operators see "stuck" / "deadline+" not just orange/red.
  • Filter chips are real <button>s with aria-pressed, so screen readers report toggle state.
  • Empty state and stuck banner are rendered as role="status" with polite live regions.

Open design questions

  • Process correlation ambiguity. When two native executors of the same tool name start within the ±1s window, do we show "native <id>" with a tooltip listing candidates, or hide the Process cell entirely? Current prototype shows the executor id plus tooltip — needs operator validation.
  • Status pill vocabulary. Spec uses running / background / deadline +. Prototype adds stuck and cancelPending as derived states. Should those be lifted into the bridge as first-class lifecycle_state values, or left as frontend-only projections?
  • Filter-chip counts currently reflect the loaded dataset, not the post-filter view. Should counts update as other chips are applied (intersection), or always remain dataset-totals?
  • Sort default. Prototype defaults to age descending (oldest first). Operators triaging stuck work may prefer stuck-then-age. Worth a usability check.
  • Density on small viewports. The dense table breaks poorly < 720px wide. OperationsRail tabs are typically pinned to a fixed minimum width, but unpinned/floating cases need a card fallback.

Divergences from PROMPT.md

  • PROMPT.md asks for "kill-signal-sent / reaped flags (if native executor)" and a mock with "exit_code = 1, reaped_at set". The runtime NativeExecutorStatus exposed via crates/defra-agent-cli/src/http/liveness.rs carries only id, pid, argv0, tool_name, started_at, age_ms. Fields kill_signaled_at, reaped_at, and exit_code live on the CLI's historical NativeExecutorRecord (trace-export shape), not on the live snapshot. Exited executors do not appear in active_native_executors. Prototype omits these and instead surfaces a derived stuck / cancelPending status driven by AgentToolCall.stuck_since + cancel_pending_remote_ack.
  • PROMPT.md asks for a per-row "Cancel" button. The design spec (§"Panel 1: Actions") explicitly rejects a per-tool cancel UX: "there is no desktop bridge command or public runtime API for per-tool UI cancellation." Prototype keeps only the spec-sanctioned Open lineage and Interrupt parent actions.
  • PROMPT.md scope #4 says "age > 60s, kill_signaled but not reaped." The spec's stuck-work auto-clear (§"Panel 5") uses a 5-second wall-clock dwell on stuck_since / cancel_pending_remote_ack. Prototype uses 5s. PROMPT.md's own Design-notes bullet also cites the 5s rule, confirming the 60s number was a draft slip.
  • PROMPT.md scope #2 includes a "completed" filter chip. The panel is scoped to live, non-terminal backgrounded tools (spec join rule "AgentToolCall.await_mode = 'background' and non-terminal lifecycle_state"). Completed rows belong to transcript history (Panel 4: CancelCause Surfacing), not this rail. Prototype drops the "completed" chip.
  • PROMPT.md names the Tauri command list_backgrounded_tools(filter?). The actual surface is desktop_operations_snapshot(request). Prototype's Design notes document the real command.

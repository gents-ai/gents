Command-policy denial surfacing in the chat transcript

The CommandPolicy validator denies certain tool invocations as a deliberate guardrail (sed --in-place, sandbox-blocked writes, network when disabled, env-var leaks). Today the denial reaches the operator as an opaque red error inline with normal tool failures. This prototype proposes a distinct amber inline block, anchored to the Lean DenialReason taxonomy, so operators see policy rejections as guardrails — not as something that broke.

Design notes

Where this anchors

The denial block lives inside the existing .tool-group in apps/desktop-tauri/src/components/Transcript.tsx — same affordances as the success / failure <details> already rendered by ToolGroups. No new top-level panel, no notification overlay. The rationale is that denials are causally tied to a specific tool call the assistant attempted in this turn; pulling them out of the transcript would lose that linkage.

The compact form is shown by default. Operators click into the full rule card the same way they click into normal tool output. For apply-time denials that have no enclosing turn (the toast variant), the prototype mounts the same vocabulary onto a top-level card in the config workspace; the rule id, category, and Lean citation are identical.

Tauri / snapshot bridge data shape

The panel reads a denied AgentToolCall row as RenderedToolCallView with an additional denial field. Today the row only carries result: String, status: String, and tool_failure_class: String (see crates/defra-agent-protocol/schemas/agent/agent_tool_call.graphql). The result string in a denial is whatever the Rust bail! in validate_command_policy produced — useful for debugging, not stable enough for the rule-id badge or the "Apply suggested fix" affordance. The Lean conformance infrastructure already speaks the richer vocabulary (see case.denial_reason, case.denied_command, case.denied_argument, case.denied_subcommand, case.denied_argv in crates/defra-agent/src/toolset/tests.rs); the persistence layer does not.

For this prototype to bind to real data, the runtime needs to enrich what it persists on a denied tool call: 

type AgentToolCall {
    /* …existing fields… */

    /* New fields (issue #286 follow-up). The Lean
       DenialReason taxonomy is the contract surface;
       toContract is the canonical string for the badge. */
    denial_reason:     String  /* DenialReason.toContract:
                                * "forbiddenPrefix"
                                * | "allowedPrefixRequired"
                                * | "readOnlyCommandNotAllowlisted"
                                * | "readOnlyArgumentNotAllowed"
                                * | "readOnlySubcommandRequired"
                                * | "readOnlySubcommandNotAllowlisted"
                                * | "readOnlyUrlRequired"
                                * | "disabledNetworkUnenforceable"
                                * | "disabledNetworkCommand"
                                * | "workspaceWriteSandboxUnavailable" */
    denied_argv:       [String]  /* full attempted argv */
    denied_command:    String    /* lookup_command, when reason carries it */
    denied_argument:   String    /* matched arg, e.g. "--in-place" */
    denied_subcommand: String    /* matched subcommand, e.g. "commit" */
    denied_prefix:     [String]  /* matched forbidden/required prefix */
    policy_mode:       String    /* "read_only" | "workspace_write"
                                  * | "unrestricted" */
    policy_network:    String    /* "inherit" | "disabled" | "enabled" */
}

The Rust validator already has the structured information available at the bail! site. The proposal is to thread it through ToolError as a structured variant and persist on the AgentToolCall write that follows. The string result stays — operators can still copy it as a diagnostic — but it stops being the only thing UI has to work with.

Lean is the source of truth for the closed set of denial reasons (Proofs/CommandPolicy/Types.lean:65-90). The frontend should treat any value outside that set as forward-compatible: render the badge with whatever denial_reason says, fall back to the category label "Policy denial", but never block on unknown values.

Distinction from tool failure

  • Color. Denial uses --color-warning (#ffa011). Tool failure stays --color-error (#ff6f5f). Operators learn the color difference once.
  • Voice. Denials read as policy statements ("read-only guard refused this argument"), failures as outcomes ("tool exited with code 2"). The category-label + rule-id badge make the policy framing immediate; failure rows have no badge.
  • Suggestion affordance. Denials carry a "suggested fix" track because the policy itself implies the fix (downgrade the behavior, swap the argument, route through a writable tool). Failures don't — runtime errors aren't deterministically actionable in the same way.
  • Recovery contract. A failure may be retried by the existing tool_retry_disposition logic; a denial is terminal for that attempt and only resolves via policy or behavior reconfiguration.

Accessibility

  • The denial dot is decorative (aria-hidden="true") and the category, rule-id, and argv carry the meaning. A screen reader hearing "Read-only guard, readOnlyArgumentNotAllowed, sed --in-place s/a/b/g README.md" gets the full picture without color.
  • Because denials are operator-visible decisions, the live surface mounts an ARIA live region (out of this prototype's static markup, but role="status" on the apply-time toast demonstrates the shape) so newly-emitted denials announce themselves.
  • The compact form keeps focus order argv → action button so keyboard operators can read and act without expanding.
  • Color contrast: --color-warning-soft (#ffd089) on --color-surface-deep (#020504) is well above WCAG AA for body text; the amber on transparent gradient is accent only.

Out of scope (matches PROMPT.md)

  • No Tauri integration, no real bridge code, no GraphQL resolver changes. This is a static HTML prototype.
  • No new denial categories. The four mock variants are drawn directly from Proofs/CommandPolicy/Cases.lean and Types.lean.
  • No changes to the validator. The "STOP and report" gate from PROMPT.md was checked: today's AgentToolCall persists the denial as an opaque result string. The prototype documents the enrichment required to bind real data, and the matrix design row (docs/superpowers/specs/2026-05-20-feature-matrix-design.md §3 command-policy) already lists operatorUi as the deferred surface this prototype unblocks.

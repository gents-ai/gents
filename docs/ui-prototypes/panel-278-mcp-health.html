Design notes — Tauri surface, data shape, K model, stuck-state, a11y

Tauri command surface (proposed)

The panel reads two commands. Both are pure reads; probe_mcp_service dispatches a one-shot probe and returns the resulting health snapshot.

// crates/defra-agent-desktop/src-tauri/src/commands/mcp.rs

#[tauri::command]
async fn list_mcp_services_with_health(
    state: tauri::State<'_, DesktopState>,
) -> Result<Vec<MCPServiceHealth>, String>;

#[tauri::command]
async fn probe_mcp_service(
    service_id: String,
    state: tauri::State<'_, DesktopState>,
) -> Result<ProbeResult, String>;

#[derive(Serialize)]
struct MCPServiceHealth {
    service_id: String,
    endpoint: String,                  // resolved per resolve_mcp_url()
    status: HealthStatus,              // healthy | stale | unreachable (projected)
    internal_state: HealthState,       // healthy | degraded | evicted | reconnecting
    failure_count: u32,
    failure_threshold_k: u32,          // HealthCheckerOptions::failure_threshold_k
    last_seen: DateTime<Utc>,
    last_error: Option<String>,
    backoff_until: Option<DateTime<Utc>>,
    last_probes: Vec<ProbeRecord>,    // bounded ring buffer (e.g. last 16)
}

#[derive(Serialize)]
struct ProbeRecord {
    at: DateTime<Utc>,
    verdict: ProbeVerdict,             // ok | fail | timeout | skipped_backoff
    latency_ms: u64,
    note: Option<String>,
}

#[derive(Serialize)]
struct ProbeResult {
    snapshot: MCPServiceHealth,
    record: ProbeRecord,
}

Implementation notes:

  • list_mcp_services_with_health() joins ToolServiceRegistry (filter status: online) against an extended ServiceHealthMap that also exposes failure_count + backoff_until. Today snapshot() only returns the public ServiceHealth (status + last_seen + last_error); the K model and backoff timestamp are currently private.
  • probe_mcp_service dispatches through run_health_check_cycle for that single service_id (already what defra-agent mcp probe does in crates/defra-agent-cli/src/commands/mcp.rs) and pushes the result onto a per-service ProbeRecord ring.
  • Live updates flow via a Tauri event channel (mcp:health-updated) emitted at the end of each run_health_check cycle. The desktop polls list_mcp_services_with_health() on event receipt rather than tick.
  • Probe button is rate-limited to one request per service per 5s (debounced client-side; the runtime ignores the in-flight duplicate).

Data shape — what the panel reads

Sourced from crates/defra-agent/src/health_checker.rs:

  • ServiceHealth { status, last_seen, last_error } is public today.
  • ServiceModelInternal { state, failure_count, backoff_until } is private and would need a public accessor or a new snapshot_full() on ServiceHealthMap.
  • HealthCheckerOptions::failure_threshold_k (the K) is configured per checker — currently a single global value (default 3); the panel renders it on each row to make the K model legible even if it becomes per-service in the future.
  • Endpoint resolution mirrors resolve_mcp_url(): prefer Tailscale IP, fall back to LAN IP, then hostname.
  • Probe history is not currently retained anywhere — the runtime keeps only the last error string. Surfacing recent probes requires a bounded ring (proposed: 16 entries per service, in-memory only, lost on restart).

K=1 vs K≥2 — why the visual distinguishes them

From the 2026-05-13-mcp-health-lean-design spec and Proofs/MCPHealth/Transition.lean:

  • K=1 — a single probeFail evicts immediately. degraded by failure-count is unreachable (only the staleness flavor is). The "K (n/N)" badge shows just K=1 with no progress bar — there's nothing to count.
  • K≥2 — probeFail increments failure_count; the service stays degraded until failure_count ≥ K, then evicts. The badge shows K=N · n/N with a progress bar so operators can see how close a flapping service is to eviction. This is the design pass tracked in #303.
  • The runtime today defaults to K=3 — the K=1 path is still witnessed by Lean conformance but is no longer the production setting. The panel surfaces whichever K the running checker is configured with.

Why surface both projected HealthStatus and internal HealthState: the projection collapses evicted and reconnecting to unreachable, which is what the agent-facing preflight gate cares about, but the operator needs the distinction to know whether the service is actively being retried or sitting in backoff.

"Stuck" — derived, not modeled

The runtime does not have a Stuck state. backoff_duration() caps at backoff_max (default 10 min) and failure_count grows unbounded while a service stays down; HealthStatus stays Unreachable the whole time. The panel derives a "stuck" badge client-side from:

  • failure_count ≥ 2 · K, or
  • last_seen older than 10 · cycle_interval (default 5 min).

This is a purely visual aid — it gives the operator an "investigate now" signal without forcing the runtime to mint a new state. If we want the same signal in the agent-facing preflight gate, the better path is a runtime threshold + dedicated transition, audited via Lean (analogous to backoffExpiry). Not in scope for this panel.

Accessibility

  • Status is conveyed by color + icon shape + text label — never color alone. The "reconnecting" pulse animation respects prefers-reduced-motion via the dot's text fallback; the dot is purely decorative (aria-hidden).
  • Service rows are <tr role="button"> with aria-expanded, focusable via Tab, and toggle on Enter/Space. Arrow keys move between rows (Up/Down). Filter chips use aria-pressed.
  • Scenario picker and filter group use role="group" with aria-labelledby referencing the visible label.
  • Probe buttons live inside each row; they stop click-propagation so clicking Probe does not also expand the row.
  • Backoff countdown updates announce as aria-live="polite" via the shell-meta block, not per-cell (avoids screen-reader spam every second).
  • All interactive elements have a visible focus ring (:focus-visible uses Source Blue, contrast-checked against the dark surface).
  • Empty state and action log both use aria-live="polite" so operators using a screen reader hear updates without polling the page.

Out of scope for this prototype

  • Real Tauri commands or DefraDB queries — all data is in-memory mock data.
  • Modifying health_checker.rs (the runtime ships from #316).
  • Multi-deployment views — assumes the operator is viewing health for a single local checker. A cross-deployment view would be a separate panel.
  • Configuration UI for HealthCheckerOptions — read-only here.
